## 5. 阶段拆解

### 5.1 OCR（NPU2）

- Structure 约 1.4–10.9 s，均值 ~5 s；高分辨率样例（病例10，3072×3897）OCR 墙钟约 **7.6 s**，仍远快于历史 CPU ~100 s。
- 占 Dual 比例很小（~5%）；**不是本批瓶颈**。

### 5.2 HaS NER（NPU0）— 主瓶颈

- 均值 **76.5 s**（17–122 s）；占 OCR+HaS **~93%**，占 Dual **~69%**。
- 根因叠加：
  1. **36 类型**医疗扩展 prompt（单次 NER 常见 6–10 s，再加多轮 residual/verify）；
  2. **3 worker 共享 NPU0**：日志大量 `waited … for shared GPU inference slot`（常见 6–65 s 排队）；
  3. 实体多时补召回轮次多（如病例9：76 entities → HaS 109 s）。
- 对比：同机单文档基线（类型更少、无并发）HaS 空页 ~1.4 s、有实体页 ~7 s。

### 5.3 LocateAnything（NPU1）

- 均值 **28.4 s**（15–41 s），启用 5 类视觉特征；相对单文档仅公章+签名时的 ~7.5 s 明显变长。
- 与 OCR+HaS **串行**：例病例8：56.39 + 18.11 ≈ 74.5。

### 5.4 队列与脱敏

- 识别并行效率 2.89×，说明 worker 调度正常，但底层 HaS 仍被闸门串行化，**业务 3 并发 ≠ HaS 3 倍吞吐**。
- 脱敏：09:31:12 – 09:34:37，12 次 `redact:dispatch`，`bbox_count` 合计 321；整单 `updated_at=09:34:38`。

## 7. 优化建议（按收益排序）

1. **HaS 并发与闸门**：批处理下限制同时进入 HaS 的 item（或为 HaS 增副本/分片），减少 `shared GPU inference slot` 等待；预估单文件 HaS 可从 ~76 s 降到接近单文档有实体水平的数倍以内。
2. **收窄类型**：医疗预设按需启用；将 36 类降到页面实际相关子集，直接缩短 prompt 与补召回轮次。
3. **Dual 真并行**：OCR+HaS ∥ LocateAnything → `dual = max(...)`，按本批均值可再省 ~28 s/文件（墙钟视争用而定）。
4. **视觉类型**：无指纹/码类场景去掉对应类，降低 LA 空检 hybrid 回退成本。
5. **超大图预处理**：病例10 类 11MP 图可先限边再推理，稳住 OCR/视觉尾延迟。
